Git & GitHub Basics

A quick, interactive guide for TPMs — no engineering degree required!

🔧 What is Git?

Git is a version control system. Think of it like "Track Changes" in Google Docs — but for code, and on steroids.

💡
TPM analogy: Imagine every change your team makes to a project plan is automatically saved with a timestamp, the author's name, and a note explaining what changed. You can rewind to any earlier version at any time. That's Git.

Git vs GitHub — what's the difference?

🛠️

Git

The tool that tracks changes on your computer. It's like the engine.

☁️

GitHub

A website that hosts Git repositories online so teams can collaborate. It's like Google Drive for code.

Key Takeaways

  • ✅ Git tracks the full history of every change
  • ✅ Multiple people can work on the same project without overwriting each other
  • ✅ You can always roll back a mistake
  • ✅ GitHub is where teams share and review those changes

📦 What is a Repository?

A repository (or "repo") is the folder for your project that Git keeps track of. It contains all your files plus the entire history of every change ever made to them.

💡
TPM analogy: A repo is like a super-powered project folder in SharePoint — it stores not just the current files, but every draft that was ever saved, who saved it, and why.

Two types of repositories

💻

Local Repo

Lives on your computer. You can work offline and experiment freely.

☁️

Remote Repo (GitHub)

Hosted on GitHub's servers. The shared "source of truth" your whole team syncs to.

Key Takeaways

  • ✅ A repo = your project folder + all its history
  • ✅ Every project has one repo (sometimes more for microservices)
  • ✅ You can see the full history on GitHub under the "Commits" tab
  • ✅ The default main branch is usually called main

💾 What is a Commit?

A commit is a saved snapshot of your changes. When a developer commits, Git takes a picture of everything that changed and stores it permanently with:

🆔
Hash

A unique ID (e.g., a3f9c2b)

✍️
Author

Who made the change

🕐
Timestamp

Exactly when it was saved

💬
Message

A short note explaining what changed

📝
Diff

The exact lines that were added or removed

💡
TPM analogy: A commit is like a version in Confluence — "v1.2 — added acceptance criteria, @alice, March 6." Except Git captures every single line that changed, automatically.

A commit timeline

1
Initial setup Bob • 3 days ago

Created the project

2
Added login page Alice • 2 days ago

Built the login UI

3
Fixed password bug Alice • 1 day ago

Fixed: passwords over 20 chars crashed

4
Add dark mode Carol • just now

Users can now toggle dark mode

Key Takeaways

  • ✅ Commits are like save points — permanent and traceable
  • ✅ Good commit messages help teammates (and future you!) understand what happened
  • ✅ You can always go back to any commit
  • ✅ Commits are local until you push them to GitHub

🌿 Branches & Merging

What is a Branch?

A branch is like a parallel copy of the project where you can safely make changes without affecting the main codebase. The main branch (usually called main) is the "official" version of the project.

💡
TPM analogy: Think of branching like creating a copy of a PRD to draft a new feature spec — you work on the copy freely, and only update the official doc after your changes are reviewed and approved.

What is Merging?

Merging is the act of taking the changes from one branch and combining them into another. This is how a feature goes from a developer's branch into the main branch — and eventually to production.

💡
TPM analogy: Merging is like folding the approved changes from your draft PRD back into the official document — carefully, so nothing important is lost.

Commit vs Merge — key difference

💾

Commit

Saves a snapshot of changes inside a branch. Like saving a draft.

🔗

Merge

Combines an entire branch into another. Like publishing the final doc.

Key Takeaways

  • ✅ main is the stable, production-ready branch
  • ✅ Always work on a feature branch — never directly on main
  • ✅ Merging brings the feature branch changes into main
  • ✅ Merges usually happen via a Pull Request so changes are reviewed first

🔀 What is a Pull Request (PR)?

A Pull Request is a formal proposal to merge your branch into main. It gives your teammates a chance to review your changes, leave comments, and approve (or request changes) before anything is merged.

💡
TPM analogy: A PR is like a change request review in your project. You submit your proposed changes, stakeholders review and comment, you address feedback, and only after approval does it go live.

The PR lifecycle — step by step

1
Create a branch

Developer creates a new branch for their feature or bug fix.

↓
2
Make commits

Developer writes code and commits changes to their branch.

↓
3
Open a Pull Request

On GitHub, open a PR: select your branch → base branch (main) → add a title & description.

↓
4
Code Review

Reviewers read the diff, leave comments, suggest changes. The author responds and updates commits.

↓
5
Approval & Merge

Once reviewers approve, the PR is merged into main. The branch is usually deleted.

What a PR shows you (as a TPM)

📊 Files changed

Every file that was added, modified, or deleted

💬 Discussions

Inline comments on specific lines of code

✅ Status checks

Automated tests that must pass before merging

🔗 Linked issues

Which tickets or issues this PR resolves

Key Takeaways

  • ✅ PRs are the main collaboration mechanism on GitHub
  • ✅ Every change to main should go through a PR (best practice)
  • ✅ As a TPM, PRs are where you can track what's being built and why
  • ✅ Link PRs to Jira/Linear tickets for full traceability

📋 Quick Reference: Common Git Commands

As a TPM you usually won't run these yourself, but it's good to know what your engineers are doing!

CommandWhat it does
git clone <url>Download a repo to your computer
git pullGet the latest changes from GitHub
git checkout -b feature/nameCreate and switch to a new branch
git add .Stage all changed files for commit
git commit -m "message"Save a snapshot with a description
git pushUpload your commits to GitHub
